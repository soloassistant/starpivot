# 真实数据出处与验证

本文件回答一个问题：**页面上出现的每一个真实对象，它的数是从哪来的、能不能自己复算。**

规矩只有一条：**观测量、标定值、模型参数三类必须分开写**。把推导值说成观测值，
是这类产品最容易犯也最不可原谅的错。

---

## 1. 取数记录（可复现）

| 数据集 | 来源 | 服务 | 取数日期 | 查询语句 |
|---|---|---|---|---|
| 真实恒星 | ESA Hipparcos Main Catalogue（VizieR `I/239/hip_main`） | VizieR TAP sync | 2026-09-26 | `select top 60 HIP,"_RA.icrs","_DE.icrs",Vmag,Plx,SpType from "I/239/hip_main" where Vmag<2.5` |
| 真实系外行星 | NASA Exoplanet Archive（`pscomppars`） | TAP sync | 2026-09-26 | `select pl_name,hostname,pl_orbper,pl_orbsmax,pl_orbeccen,pl_bmassj,pl_rade,st_mass,st_rad,st_teff from pscomppars where hostname in ('TRAPPIST-1','TOI-178','ups And','51 Peg','Proxima Cen') order by hostname,pl_orbper` |

落地文件：`data/real_stars.json`、`data/real_exoplanets.json`。
数据已**落地成文件**，因此离线可用、可复现、可 diff —— 不依赖取数时网络可达。

### 两个踩过的坑（记下来免得重踩）

1. **`ps` 表不能直接取。** 同一颗行星会因不同文献出现多行，参数互相矛盾。
   必须用 `pscomppars`（每颗行星一行最佳综合值）。
2. **VizieR `I/239/hip_main` 的位置列叫 `_RA.icrs` / `_DE.icrs`**，不叫 `RAdeg` / `DEdeg`；
   用后两个名会报 `Unknown column`。

## 2. 观测量 / 标定值 / 模型参数：三类分开

### 2.1 系外行星（这一层链条最短，全部是观测量）

| 字段 | 类别 | 说明 |
|---|---|---|
| `pl_orbper` | **观测** | 轨道周期，凌星/视向速度观测 |
| `pl_orbsmax` | **观测**（由周期与恒星质量导出，或动力学拟合） | 半长轴 |
| `pl_orbeccen` | **观测** | 偏心率 |
| `pl_bmassj` | **观测综合值**（性质随探测方法而异，见下） | 质量（木星质量） |
| `pl_rade` | **观测** | 半径（地球半径） |
| `st_mass` / `st_rad` / `st_teff` | **观测** | 宿主恒星的质量/半径/有效温度 |

**这一层不需要任何标定链**：`a` 与 `e` 可以直接喂进 N 体。这是三层真实数据里最干净的一层。

**但"能喂"不等于"数据给全了"。** 跑 N 体需要三维初始状态，逐项对一下 Archive 给了什么：

| 三维初始状态需要 | Archive 这张表给了吗 |
|---|---|
| 半长轴 `a` | ✅ `pl_orbsmax` |
| 偏心率 `e` | ✅ `pl_orbeccen` |
| 倾角 `i` | ❌ 没有 |
| 升交点经度 `Ω` | ❌ 没有 |
| 近心点方向 `ω` | ❌ 没有 |
| 起算相位 `M0` | ❌ 没有 |

所以预设里那四个角是**页面自己摆的**：一律取 0，等于"共面、且所有行星都从近心点起算"。
**这是模型假设，不是观测** —— 画面上"行星排成一线"就是这么来的。
判据 `_probe_realpage.js` 把两件事一起钉住：这四个角确实全是 0，且每组预设的说明里
必须写明"朝向与相位是假设"（不写，就等于让用户以为三维初始状态也是观测来的）。

**关于行星质量的性质：不是"一律是下限"，别写错。**
质量的性质**随探测方法而异**：视向速度给的是 `m·sin i` 的**下限**；而凌星多行星系统
（TRAPPIST-1、TOI-178）的质量来自**凌星计时（TTV）**，那是拟合出来的质量，不是下限。
`pscomppars` 的 `pl_bmassj` 是 Archive 给出的综合值，而**我们的数据文件没有记下每颗的方法**。
于是在记下方法之前：
- 页面**不能**把它说成精确测量值，**也不能**说"一律是下限"（对 TTV 系统那句话就是错的）；
- 已落地的口径（页面预设说明原文）："质量性质随探测方法而异（视向速度给的是 m·sin i 下限，
  凌星计时给的是拟合出的质量），本表未逐颗记录方法，所以这里不把它当成精确测量值"；
- **待办**：把 `pl_bmassprov`（质量出处）与不确定度一列一起取下来，才能逐颗标注
  "实测 / 下限 / 拟合"。在那之前，任何"这颗行星有多重"的确定说法都不许出现。


### 2.2 恒星（观测 + 标定，必须分开）

| 字段 | 类别 | 说明 |
|---|---|---|
| `HIP` / `RA` / `Dec` | **观测** | 编号与 ICRS 天球坐标 |
| `Vmag` | **观测** | V 波段视星等 |
| `Plx` | **观测** | 三角视差（mas） |
| `SpType` | **观测归类** | 光谱型串（含光度级与备注，如 `O9.5Ib SB`） |
| `d`（距离） | **推导** | `d = 1000 / Plx`（pc）—— 纯算术，无标定 |
| `M_V`（绝对星等） | **推导** | `M_V = Vmag − 5·log10(d) + 5` —— 纯算术，无标定 |
| `T_eff` | **标定** | 由光谱型查标定表 —— **待接入，需引用具体表** |
| `BC`（热改正） | **标定** | 由 `T_eff` 查表 —— **待接入，需引用具体表** |
| `L`（光度） | **推导** | `M_bol = M_V + BC`；`L = 10^((M_bol,☉ − M_bol)/2.5)` |

**还没做完的地方，明写在这里**：`T_eff` 与 `BC` 两张标定表尚未接入，因此**恒星的
温度与光度目前算不出来**。在接入之前，页面只能显示观测列（坐标、视星等、视差、光谱型）
与两个纯算术推导列（距离、绝对星等），**不能显示 T 与 L** —— 宁可不显示，也不编。

> **注意这与系外行星宿主那一层不是同一件事。** 系外行星的宿主不走光谱型标定链：
> `st_teff` / `st_rad` 是 Archive 直接发表的**观测值**（由光谱拟合或干涉测量得到），
> 不需要任何标定表。所以那五颗宿主**可以**显示 T 与 L，而 `real_stars.json` 里的
> 60 颗 Hipparcos 恒星**不可以** —— 差别在于"这个数是谁给的"，不在于"它是不是恒星"。
> 判据 `_probe_obsstar.py` 与 `_probe_realpage.js` 钉的就是前者；后者的门仍然关着。

### 2.4 单位换算因子：也必须只有一份

`real_exoplanets.json` 里带一个 `conversions` 字段：

```json
"M_jup_to_Msun": 9.5458e-4, "R_earth_to_km": 6371.0, "R_sun_to_km": 696340.0
```

| 因子 | 类别 | 说明 |
|---|---|---|
| `M_jup_to_Msun` | **单位换算** | IAU nominal `GM_Jup/GM_sun`；把 `pl_bmassj` 换成内核的 M☉ |
| `R_earth_to_km` | **单位换算** | IAU nominal；把 `pl_rade` 换成 km |
| `R_sun_to_km` | **单位换算** | IAU nominal，与内核 `bodytype.cpp` 的 `kRsun_km` 同源 |

**为什么放在数据文件里、而不是写进页面或判据**：这些数必须有唯一一份。页面要拿
`pl_rade` 拼 `--body`，而它只能读数据文件里这一份；判据也读同一份。谁自己抄一遍，
就会在某个时刻出现两个只差一点的木星质量 —— 而两边都"能算"，谁都不会报错。
`_probe_obsstar.py` 有一项专门断言"文件里的因子 = 判据独立知道的 IAU nominal 值"，
`_probe_realpage.js` 则在页面侧用同一个字段建预设。

## 3. 验证（判据 `_probe_realdat.js`，25 项）

验证的原则：**用外部已发表值或物理定律复算，不用我们自己的推导值自证。**

### A 组：开普勒第三定律互校（系外行星）

由**实测半长轴 a** 与**实测宿主质量 M** 算 `T_pred = √(a³/M)`，与**实测周期**比。
两者来自不同观测量（周期来自凌星计时，a 来自动力学/星质关系），能对上就是硬证据；
同时这也验证了内核 `G = 4π²` 的单位制约定。

实测结果（19 颗全部参与）：

| 系统 | 宿主质量 | 相对偏差范围 |
|---|---|---|
| TRAPPIST-1（7 颗） | 0.0898 M☉ | 0.0034% – 0.0601% |
| TOI-178（6 颗） | 0.647 M☉ | 0.1420% – 0.2581% |
| ups And（3 颗） | 1.30 M☉ | 0.0010% – 0.0057% |
| Proxima Cen（2 颗） | 0.1221 M☉ | 0.2321% – 0.2406% |
| 51 Peg（1 颗） | 1.07 M☉ | **1.0351%** ← 见下 |

**关于 51 Peg b 的 1.0351%（这条必须解释清楚，不能含糊地说"在容差内"）**：
Archive 里它的半长轴写的是 `0.052`，**只有 2 位有效数字**（其余行星有 5–8 位小数）。
由实测周期反推应为 `0.052365 AU`，把 0.052365 四舍五入到 3 位小数正好是 `0.052`。
所以这 1% 完全由**发表的舍入**解释，不是抄错。判据因此按 **a 的书写精度分档**：

- `a` 写到 ≥5 位小数的 12 颗：最大偏差 **0.2406%**（阈值 0.3%）✅
- 全部 19 颗：最大偏差 **1.0351%**（阈值 1.5%，用于抓抄错一位）✅
- 偏差最大的那颗恰好属于「书写精度最低」档 ✅

另有 8 项结构判据：偏心率全部落在 [0,1)（否则内核直接拒绝）、缺项保持缺失不补零、
TRAPPIST-1 七颗的**周期与半长轴双向单调递增**（抄错一位就会被抓住）、
所有宿主质量都在氢燃烧下限 0.08 M☉ 之上（否则系统里一个光源都没有）。

### B 组：视差 → 距离 → 绝对星等（恒星）

用**已发表的绝对星等**做外部锚点（不是我们的推导值）：

| 恒星 | 本链路算得 | 已发表 | 差 |
|---|---|---|---|
| 天狼星 A | d=2.637 pc，M_V=1.454 | 1.42 | 0.034 mag |
| 参宿四 | d=131.062 pc，M_V=−5.137 | −5.14 | 0.003 mag |
| 参宿七 | d=236.967 pc，M_V=−6.693 | −6.70 | 0.007 mag |
| 南河三 | d=3.497 pc，M_V=2.681 | 2.66 | 0.021 mag |
| 五车二 | d=12.938 pc，M_V=−0.479 | −0.50 | 0.021 mag |

全部落在容差内，且视差最大的那颗（HIP 32349，Plx=379.21 mas）正是天狼星 ——
已知最近的恒星之一，与常识一致。

**刻意不做的事也有判据钉住**：恒星表条目里**只有观测字段，没有自造的星名字段**。
「HIP → 中文星名」那张对照表不在本数据的来源里，凭印象写会引入无法追溯的错误。
要加星名，就得从权威表另取一次并记录出处。

## 4. 观测覆盖：把「某一类星」换成「这一颗星」

这是本轮新增的、也是整条链上最容易出错的一环：**类型表给的是"这一类星"的代表值，
真实个体必须用观测值。**

### 4.1 内核的优先级与来源标注

`--body` 支持两个可选的 key=value 字段：

```
--body "name,a,e,inc,raan,argp,M0,mass|type:mass[,radius_km][,teff_K=..][,lum_lsun=..]"
```

内核按下面的顺序决定一个发光天体的 T 与 L，并在 JSON 里回显 `t_eff_src` /
`luminosity_src`，页面据此如实标注每一个数的来源：

| 情形 | `luminosity_src` |
|---|---|
| 显式给了 `lum_lsun=` | `given` |
| 给了 `radius_km` **且** 给了 `teff_K=`（没给 L） | `derived_from_radius_and_t_eff` |
| 声明了类型 | `type_grid` |
| 没类型、质量在氢燃烧下限之上 | `mass_luminosity_relation` |
| 不发光 | `none` |

**第二行是"真实数据能不能接进来"的关键。** 真实编目（`pscomppars`）里**没有** `st_lum`，
只有 `st_mass` / `st_rad` / `st_teff`。所以内核必须能只靠 (R, T) 得到 L：

```
L = (R/Rsun)² · (T/Tsun)⁴      ← 斯特藩-玻尔兹曼，与 sb_radius_km 互逆
```

否则页面就得自己写这个式子 —— 那就把物理抄进了页面，而本项目的规矩是页面一个数都不算。
这一支**排在类型表之前**：类型表给的是"这一类星"的代表光度，而 (R, T) 是"这一颗星"的
观测值，用类型表的数去乘它们等于把观测值扔掉。

**边界（判据钉住）**：只给 `teff_K=` 而不给 `radius_km` 时**不推 L**，退回类型表。
因为那时 R 是未知量，硬推等于替用户编一个半径，再拿这个编出来的数去算行星温度。

派生的一点：**宿主不声明类型。** 数据里没有光谱型，套一个"某类星"的类型名就是替用户
编分类；而 (质量, 半径, 温度) 已经足够内核判定发光（氢燃烧下限 0.08 M☉）并由 (R, T)
推出光度。判据 J 组把这条路径的四个后果逐条验过。

### 4.2 反例：为什么非做不可

TRAPPIST-1（0.0898 M☉）刚好在氢燃烧下限 0.08 之上，于是走类型表/质光关系那条路：
`L ∝ M^3.5` 只给 **2.17e-4 L☉**，而由观测 (R, T) 推出的是 **5.53e-4 L☉** —— 差 **2.56 倍**。
这不是"显示得不好看"：辐照度 `S = L/r²` 直接决定行星在不在可居带。
TRAPPIST-1 e 的地表温因此从 **261.9 K 掉到 214.0 K**（差 48 K），
页面会把一颗本该宜居的行星如实显示成"冻结"。

对照组（把宿主观测值摘掉再发一次）在五个系统上给出的差距**方向并不一致**：

| 系统 | 宿主质量 | 观测 L / 模型 L |
|---|---|---|
| TRAPPIST-1 | 0.0898 M☉ | **2.55×**（模型偏暗） |
| Proxima Cen | 0.1221 M☉ | **1.98×**（模型偏暗） |
| 51 Peg | 1.07 M☉ | 1.10× |
| ups And | 1.30 M☉ | 1.25× |
| TOI-178 | 0.647 M☉ | **0.63×**（模型偏**亮**） |

方向不一致这件事本身就说明：这不是"差一个常数"，而是模型在两端都不准。
所以不能靠"调一个系数"修好，只能按个体给观测值。

### 4.3 验证（判据 `_probe_obsstar.py`，40 项）

| 组 | 内容 |
|---|---|
| A | 先校准判据自己：SI 复算太阳应当回到 1 L☉（实测 1.00601，偏差 +0.601%） |
| B | TRAPPIST-1：观测覆盖真的进了内核，且能被 SI 路径独立复算 |
| C | 半径推导路径：只给 L 与 T 时 `R = Rsun√L/(T/Tsun)²`（0.30% vs 0.601% 容差） |
| D | 每颗行星的初值逐个对齐 `real_exoplanets.json`（容差按 `%.6g` 的最坏量化误差定） |
| E | **开普勒第三定律**：用接线后的 a 与宿主质量算周期，对实测周期（最大偏差 0.0601%） |
| F | 反例仍在（2.56 倍、48 K）—— 若哪天质光关系被修好，这一项会失败并提醒可以撤掉覆盖 |
| G | 四条负路径：给岩石行星设亮度 / 未知 key / `teff_K=0` / 忘了写等号 |
| H | 其余 4 个真实系统；**缺测项按缺失处理，不补零**（排除 TOI-178 b，缺 `pl_orbeccen`） |
| I | 只给 (R, T) 时 L 由内核推出；差值恰好 = 常数集固有偏差（+0.6010% vs +0.6010%） |
| J | 页面真实发出的那种消息：宿主**不声明类型**，只给 (质量, 半径, 温度) |

容差是怎么定的（这一条本身踩了两次）：JSON 里 `a_AU` / `e` / `mass_msun` / `radius_km`
都用 `%.6g` 打印，最坏相对量化误差是 `0.5e-5 / mantissa`（mantissa ∈ [1,10)）
→ 最大 **5e-6**。先卡 1e-9 误报"半径对不上"，改成 2e-6 之后 TOI-178 的 1.7e4 km 量级
又误报 —— 因为它恰好落在"mantissa 接近 1"那一档。**容差必须按最坏情况定，
不能按手头这组数定**：手头这组碰巧是好数就测不出真错，恰好是坏数就误报。

### 4.4 页面侧（判据 `_probe_realpage.js`，50 项）

数据 → 页面函数 → 网关 → 内核，四层。前三层不需要服务，最后一层走真 HTTP。

**这一层第一轮就抓到四个真问题**（都不是本轮新引入的，是本来就在的）：

1. **类型键大小写被静默丢掉。** `sanitizeBody` 的类型校验写的是 `[a-z_]`，而内核 39 个
   类型键里有 **21 个带大写**（`O_V` / `M_V` / `WR` / `G_III` / `M_0`…）。于是光谱型的星
   只要经过一次 `sanitizeBody`（恢复会话、套预设都会经过）就被降级成"没声明类型"，
   半径跟着落回页面默认的 **6371 km** —— 一颗太阳被画成地球那么大，而屏幕上不报任何错。
2. **预设不复位碰撞设置。** 玩完「行星撞地球」（`collide=fragment`、半径放大 450×）
   再点「真实：TRAPPIST-1」，那 450 倍会跟着过去，真实行星在你眼前被撞碎。
   预设必须定义**完整**状态，"上次剩下的"不算。
   （同理复位了积分器：切到 hermite 之后按一个没写 `integ` 的预设，应当回到默认蛙跳，
   否则"这个预设算出来是这样"这句话不成立。）
3. **容差按手头那组数定，而不是按最坏情况定**（见 4.3 最后一段）。
4. **页面替用户编了一个观测半径。** 从类型调色板点画面放一颗黑洞时，`placePlanetAt`
   无条件写了 `radius_km: 6371`，同一行上方的注释写的却是"半径交给内核算" ——
   注释在说一件事、代码在做另一件。而 `sanitizeBody` 只认"这个字段在不在"，
   于是"我没给半径"被变成了"我给了个地球大小的观测半径"：点一颗黑洞得到的是
   **半径 6371 km 的黑洞**，而正确的值是按 G 和 c 算出的史瓦西半径 **29.53 km**。
   这不是显示问题 —— 半径会进 (R,T)→L 的推导、再进行星温度的辐照度。
   修法是**选了类型就不给这一格**（留空本身就是一句话），而不是让页面去算史瓦西半径：
   页面一个数都不算这条规矩没有例外。判据把两件事一起钉住：
   下发 payload 里黑洞这颗没有 `radius_km`，且页面最终显示的是内核回算的 29.5334 km。

## 5. 碰撞 / 碎裂链路上的四个真问题（判据 `_probe_collide.py`，45 项）

这一层与其他层不同：它验的不是"数对不对"，而是**"这一跑会不会崩、会不会失控"**。
所以它必须是 python 而不是走录制回放 —— 一段录制回答不了"这一次到底崩没崩"。

先说三条**语义**（不是实现细节，判据就钉在它们上面）：

| 约定 | 内容 | 为什么必须写下来 |
|---|---|---|
| 登记表只增不减 | 死亡天体标 `died_at`，**不删行**；碎裂把新行 `push_back` 进去 | "行数"因此不等于"天体数"，两者各自有意义 |
| `max_bodies` 限制的是**存活**天体 | 不是输出规模 | 实测最坏情况 64 存活 / **14735 行** / 165 秒 —— 帧根本渲染不出来 |
| 帧是**按当时存在的行**发出的 | `born_at <= t` 的行才进这一帧 | 帧长会随事件增长（实测 798×3 → 2203×7），不是恒定 `len(bodies)` |
| 质量守恒要算**存活集** | 不是整张登记表 | 整表求和会重复计入被并掉的那一行（实测 1.000009 vs 1.000006） |

四个真问题：

1. **`--collide fragment` 一发生真实撞击就段错误**（Windows 退出码 3221225477、stderr 全空）。
   根因：五组按 `reg.size()` 初始化的数组（`sprops` / `lum_of` / `var_phase` / `type_of` /
   `lum_series`）声明在了 `handle_collisions` **之后**，而碎裂会让 `reg` 变长 ——
   于是后面的按下标遍历越界。修法是把这几个声明移到碰撞处理之前，并在每次碎裂时一起增长。
2. **碎片环太窄 → 碎片立刻再次相撞，级联炸开。** 碎片被放在一个环上，而环半径必须严格大于
   相邻碎片的**接触距离**（`d <= r_a + r_b` 把"接触"也算成碰撞）：
   `ring > (spread/n^(1/3)) / sin(π/n)`。修法是取两者较大值再乘 1.02 的余量，
   并把**实际用的环半径**写进事件 JSON（`ring_AU`）与 `CollisionEvent::ring_radius` ——
   免撞期本来就是由它算出来的，之前用的是另一个半径，两者不一致。
3. **没有登记表行数上限 → 最坏情况跑不动。** 补上 `kMaxRegistryRows = 4 × max_bodies`
   之后，同一情形从 **165 秒 / 14735 行** 变成 **1.6 秒 / 255 行**。
   注意这是**两个**上界（存活数、行数），要分别设、分别测。
4. **`loadRealSystems()` 覆盖了预设区的说明文字。** 真实数据接进来之后，
   它在 `#presetnote` 上用了赋值而不是追加，把原有的帮助文字顶掉了。
   是 `_probe_play_modes.js` 的"预设区有说明文字"那一条抓到的 —— 判据写在那里，
   所以它变成了"看得见"的回归，而不是等用户来问。

**这条链路上最值钱的一条经验：改完必须重测。**
第 2 条修完之后我预测级联已经收住；重测发现最坏情况**仍然是** 165 秒 ——
真正起作用的是第 3 条那两个上界。所以判据里有一条**最坏情况**断言
（色散给 0、最小速度给 0、碎片数给满），否则永远只在顺手的那组参数上绿。

## 6. 判据自身的方法论（三条，都是被自己的判据教出来的）

### 6.1 容差按最坏情况推导，不按手头这组数试

已在 4.3 记过一次，本轮**又犯一次**（另一个文件里）：说"逐位相同"（1e-9）去比 `%.6g`
打印出来的字段。结论不变且要当纪律执行：`%.6g` 的最坏相对量化误差是
`0.5e-5 / mantissa` → 最大 **5e-6**，所以容差 **1e-5**，处处一致。

### 6.2 负样本必须走与被测项同一个函数

`_check_session.js` 里想把"坏脚本会被抓到"自证一遍，写的是
`/SyntaxError/.test(e.message)`。而 `SyntaxError` 的 `message` 里**只有**
`Unexpected end of input` 这类细节、**没有类名**（类名在 `e.name`）——
这条断言因此永远不可能通过。它确实红了，但红的原因是负样本自己写错了，
与被测的那处检查毫无关系。**恒失败的负样本不是负样本，是噪音。**

### 6.3 「保护写着」不等于「保护在生效」，且屏障要能被证伪

内核探针链上有一道"录制必须对得上当前二进制"的屏障，理由是避免拿旧内核的输出喂新内核的
断言。但它**一直是空转的**：录制文件里没有写指纹，于是校验函数那句 `!meta.exe_size`
恒为真、永远返回"对得上"。写完后用**假指纹**证了一次：回放必须报"整份作废"而不是照跑。
只有体积一项也仍不够（改几行而字节数不变的重建挡不住），所以现在体积 + sha1 都核。

同类的还有一条**顺序**上的：预热/收集那一段需要它收集的探针所用的环境变量
（jsdom 探针要 `NODE_PATH`），而那个变量当时设在了它**之后**的那一层 ——
于是探针在 `require('jsdom')` 处直接退出码 1、一条命令都没收到，
而循环只 `break` 不吭声。缺口要等到后面一层回放时才以"某条命令没录到"的面目报出来，
看着与真实原因毫不相关。现在两件事一起做：环境变量设在最前面，收集轮的退出码当场判读。

## 7. 轨道页那三份"冻结样本"（`viewer/demo.js`）：不可重生成，但可逐位复核

这一条是补出来的 —— 起因是全仓探针只加载 `/universe.html`，**轨道页的脚本从来没被执行过**。
补的过程中发现：`demo.js` 的生成脚本 `tools/make_demo_data.py` **已被删掉**，工程也**不是 git 仓库**
（`git rev-parse` 报 `not a git repository`），所以这份文件**永远无法按原样重生成**。
它又恰恰是页面上写着"确实是 CLI 算出来的真结果"的那份数据 —— 内核物理一旦改动，
它会变成"看起来像真结果"的旧数，而**没有任何判据会红**（它不参与编译）。

**复核命令（已实测逐位一致，判据 `_probe_orbit_data.py` 11 项）**：

```bash
starpivot propagate --a 7078  --e 0.001   --inc 98.2 --raan 0 --argp 0   --hours 24 --step 30
starpivot propagate --a 6798  --e 0.0005  --inc 51.6 --raan 0 --argp 0   --hours 48 --step 30 --drag 1 --area 10 --mass 210000
starpivot propagate --a 26560 --e 0.74    --inc 63.4 --raan 0 --argp 270 --hours 12 --step 60
```

参数全部**从样本自己身上读出来**（`model` / `initial_elements` / 最后一个点的 `t_s`），
没有一处靠猜。三个场景共 **2 083 个采样点**的各分量 + `model` / `secular_drift` /
平均根数（起末）/ 末态密切根数 / `epoch_utc` / `osculating_minus_mean_a_km` **全部逐位相同**。

**采样间隔为什么是 120 / 270 / 60 s 而步长是 30 / 30 / 60 s**：内核自己抽稀，
`out_every = max(1, steps / 600)`。这个数在 `tools/starpivot_cli.cpp` 里，不在样本里 ——
不读那行会把"点数对不上"当成结论。

**第二条（阻力那一条）为什么差点没法复核**：阻力只通过 `A/m` 进入方程，
而样本原先**只记了 `drag: true`、没记面积/质量**。第一次比对差 1.06 倍，
差点写成"样本与今天的内核不符"。判决性实验：**用一个标量去拟合** ——
若某个 `A/m` 能让 641 个点（× 3 分量 = 1 923 个打印过的数）**逐位**复现，
那只能是"参数没记"而不是"物理变了"。实测解出 `A/m = 4.7619e-5`（即 10 m² / 210 t），
**641/641 逐位相同** → 物理没变。

**根治在内核那一端（一处收口）**：`propagate` 现在会在航天器参数**真的进入物理**时
（`--drag` / `--srp`）回显 `model.spacecraft = {area_m2, mass_kg, cd, cr, area_over_mass_m2_per_kg}`；
`--mass 0` 时 `A/m` 没有定义，**省略该键**而不是写 0（"没给"和"给了 0"是两句话）。
样本里补齐了这一行（与内核回显逐字一致），页面也把它显示出来 —— 否则看的人仍然不知道
"两天掉 0.0054 km"对应的是什么飞行器。

**另一处同类错（页面上用户可见）**：「关键量」表的"周期"原先读 `m0.period_s`，
而内核的 `mean_elements_*` **从来没有回显过这个键**（只有 `initial_elements` 里有 `period_s`）
→ `(…||0)` 把它**安静地**显示成 `0 s (0.0 min)`，三个场景全一样。
实证方式是**把页面自己的 `kvTable` 抠出来喂真样本**，看它渲染出什么（不是读代码猜）。
已改为读真正回显它的那一处，缺失时给「—」。判据 `_check_orbit.js` 第 5 条
（页面读的每个字段名都必须在样本里存在）就是为这一类错立的。
