Linux 交叉编译（供参考，与 WASM 路线并列）：

| 尝试 | 命令 | 结果 |
|---|---|---|
| 交叉编译到 Linux（gnu） | `zig c++ -target x86_64-linux-gnu -static` | 失败：`libc of the specified target requires dynamic linking` |
| 交叉编译到 Linux（musl/gnu，不带 static） | `zig c++ -target x86_64-linux-musl` / `-gnu` | 挂住 >7 min，已终止（本机脚本无外网） |

WASM 路线（这一张是本次真正逐项验过的，**"能编译"和"能用"是两件事**）：

| 尝试 | 结果 |
|---|---|
| 单个 TU（`gravity.cpp`）编到 `wasm32-wasi` | 产出目标文件 —— 上一版本文档引以为据的就是这一条。**它不是可运行模块**，证明不了任何"浏览器能跑" |
| **`src/*.cpp`（14 个 TU，整个内核库）链成 WASI 模块** | ✅ **成功，1 892 576 字节（由 `_probe_wasm.py` 实测）** |
| **用真 WASI 宿主（Node 22 `node:wasi`）加载并执行该模块** | ✅ **成功**：编译 → 实例化 → `_start` 返回 0 |
| 把 `tools/starpivot_cli.cpp`（CLI）一起链进去 | ❌ **失败**：`wasm-ld: undefined symbol: __cxa_throw / __cxa_allocate_exception` |
| 同上再加 `-fwasm-exceptions` | ❌ **编译器内部错误**（clang 崩，要求提交 bug report），此路不通 |
| 一个可被页面调用的 C ABI 入口 | ❌ **不存在**：`cmd_nbody` 是 796 行的单体 CLI 函数（argv 进、printf 出）；库里没有"跑一个场景并交回帧"的函数，`system.hpp` 只暴露 `Body` / `System` 两个结构 |

结论，精确到不能再退：

- **已证实**：这颗内核的**库**能编成 WASI 模块，并且**能被真 WASI 宿主实例化执行**。
  也就是说"浏览器里跑同一个内核"在技术上没有被证伪 —— 最容易被怀疑的一步（链接 + 实例化）已经过了。
- **未证实**：模块**在浏览器里**实例化（浏览器要自己提供 WASI 导入，与 Node 不是一回事）；
  以及**页面怎么喂参数、怎么收结果** —— 这正是"编成 WASM"最容易骗过自己的地方。
- **已知的两个障碍**（都不是猜测，是上面那两行报错）：
  ① **页面入口不能复用 CLI**：CLI 里有一个 `throw`（`starpivot_cli.cpp:1412` 的输入校验），
  而 wasm 目标没有异常运行时、`-fwasm-exceptions` 又会崩编译器；所以要新写一个
  **不抛异常、不走 argv/stdout** 的入口点。
  ② **内核要把"跑一次"抽出来**：`cmd_nbody` 把解析 / 组装 / printf 揉在 796 行里，
  要给页面用就得抽出"配置进、帧出"的纯函数。
- 因此状态是：**WASM 编译验证通过（库）；浏览器实例化与接口集成未验证。**

**所以"正式站不需要服务器跑 C++"这句话，现在只能算一个待证的目标**，不能当成已成立的事实
（见 §5 第 14 条那个最小验收：浏览器里给一组初始条件 → 调 WASM → 拿到位置数据 → 画出来）。

## 4. 上线架构：一个必须如实交代的约束

### 4.1 硬约束

内核是 **C++17**，网关是 **Python 薄转发层**（`webapp.py` 只转发、不算数），页面是静态 HTML。
线上要真算，就需要**一个能在目标环境里执行起来的 C++ 产物** —— 传统答案是 Linux 二进制，
另一条是把内核编成 WebAssembly 模块（见 4.3）。**两条都要过，只是过的地方不同。**

### 4.2 本机实测结论（不是猜测）

**结论先行：可部署的 Linux 二进制已经做出来了**（下表第三条），并且**已经在云端跑起来**
（§0.5 的"上线"一行）。所以本文档更早那句"已确认交叉编译不可用"是**错的**，
后一版"本机尚未成功构建"也**已过期**。

两版错误是同一个病根，值得单独记下来：

> **把"试了几次没成"写成"这条路不通"，是最容易犯、也最容易一路传下去的过度概括。**
> 那个"挂住 >7 分钟"根本不是失败信号 —— 是 zig 在**从源码编 musl libc**。
> 我们把它读成了"疑为需联网取 libc"，于是给这条路线判了死刑，
> 转而去做 WASM，还把这个结论写进了风险表和交付计划。**多等两分钟，整条路就通了。**
> 判据应该是"命令还在不在干活"（缓存目录有没有新文件、CPU 在不在转），
> 而不是"我等了多久"。

| 尝试 | 命令 | 结果 |
|---|---|---|
| 交叉编译到 Linux（gnu） | `zig c++ -target x86_64-linux-gnu -static` | **失败**：`libc of the specified target requires dynamic linking` |
| 交叉编译到 Linux（musl/gnu，不带 static） | `zig c++ -target x86_64-linux-musl` / `-gnu` | 当时判为"**挂住**（>7 min）"并终止 —— **这是误判**，见上 |
| **交叉编译到 Linux（musl，静态）** | `zig c++ -target x86_64-linux-musl -std=c++17 -O2 -ffp-contract=off -Iinclude -o … src/*.cpp tools/starpivot_cli.cpp` | ✅ **成功**：**3 分 26 秒**，**8 758 552 字节**，静态 x86-64 ELF（程序头里没有 `PT_INTERP`，不依赖目标机 libc） |
| 脚本直连外网 | node `fetch` 到 Exoplanet Archive / VizieR / JPL | **全部失败**（`fetch failed`）；本机无代理在跑（PAC 是残留配置），DNS 正常 |
| **脚本直连外网（复核）** | `curl` 与 **python `urllib`** 到 celestrak.org | ✅ **通**（实测取回真实 TLE 并参与计算）。<br>**所以"本机脚本无外网"这个说法过宽，已更正**：不通的是 **node 的 `fetch`**（很可能就是那条残留 PAC 配置在影响 node）。当初由一次 node 失败推出"整台机器没有外网"，是同一个病根：**把一次观察当成了规律** |
| 发布沙箱的外网 | 线上 `/api/find-close` 取 CelesTrak | ✅ **通** —— 线上返回了真实接近事件（含 `miss_km` / `tca_utc` / `rel_speed_kms`）。一度以为"沙箱没外网"，实际是**分组名过期**（见 §6） |
| WebFetch（应用自带通路） | 上述三个数据源 | **通**（拿到了真实数据，见 2.1 / 2.2） |

### 4.3 实际走通的上线路线（以及 WASM 现在的身份）

**走通的是这一条：Linux 静态二进制 + 原有 Python 薄网关，整体作为单端口 HTTP 服务发布。**

- 内核用 `zig c++ -target x86_64-linux-musl` 编成**静态** x86-64 ELF（8 758 552 字节），
  放在 `kernel/linux-x86_64/` —— **不能放 `build/`**：发布包会排除构建产物，
  放错了就是"本地测得好好的，上传之后沙箱里根本没这个文件"；
- 网关 `webapp.py` 平台无关地挑内核、听 `PORT`、绑 `0.0.0.0`、启动时补可执行位；
- 发布后**逐项验证**（健康检查 / 跨平台逐帧同值 / 真实数据链路 (R,T)→L / 负路径报错同句），
  证据见 §0.5 的"上线"行。
- **架构一个字没改**：仍然是"页面只画、网关只转发、内核真算"，只是内核这次跑在 Linux 上。

**WASM 因此从"首选"降为"可选优化"，不再在交付路径上。**
它的价值依然成立（内核进浏览器 ⇒ 连服务器都不用，静态站也能真算），
但**不再是上线的必要条件**。已证实的部分保留在 §0.5 与判据 `_probe_wasm.py` 里；
要真做完还差两件已定位的事：页面入口点**不能复用 CLI**（那个 `throw` 让链接不过，
而 `-fwasm-exceptions` 又崩编译器），以及 `cmd_nbody` 那 796 行要抽出"配置进、帧出"的纯函数。

**回放路线（静态站 + 预生成结果）继续留着当"万一"，但本轮没用上**，而且它现在已经不便直：
`make_demo_data.py` **已不在仓库里**（清理时删掉了），两个页面又都直接打 `/api/*` ——
纯静态发布的结果是"页面能开、一点算全废"。要用这条路，得先把生成管线补回来。

**始终不接受的做法**：把别人的前端天文库结果当成"我们的内核算的"。

| **数据精度不足以支撑统一的硬阈值** | 中（`a` 的书写精度逐颗不同，最粗的只写了 2 位有效数字） | 阈值**跟随数据源的书写精度分档**，而不是定一个统一数字再让数据去凑（§5 第 6 条）。若将来要求更严，就必须换精度更高的数据源，**不能靠放宽阈值假装通过** |
| 数据源变更或限流 | **已经发生过一次（实例）**：CelesTrak 的 `GROUP=iridium` 现在返回 `Invalid query: … (GROUP=iridium not found)` —— 分组名被上游改掉了，而我们页面上的默认三组里就有它（`iridium,globalstar,orbcomm`）。好消息是另两组仍在供数，所以功能照常可用；坏消息是**它坏得没有症状**（少拉一组，静默少算）。<br>另：CelesTrak 对**连续请求会限流**——我对着它连打十几个请求时，同一个 `stations` 组先返回 60 颗、后返回 0 颗。**所以"某个组没数据"这件事不能靠连续探测来判定**（会把限流误读成改名） | ① 取到的数据**落地成文件**并记录取数日期与查询语句；② 对**实时**源（CelesTrak）要单独做一次数据源合规性核对（本机已有 `external-feed-vetting` 技能专门讲这个：分层实测、用真实死源当负路径 fixture、"可用 ≠ 能用"），**不要拿一次被限流的样本去改分组名** |
| 范围蔓延成"产品官网" | 中 | 非目标已写明；V4.0 只做工具站 |

**不成立的条件**：如果 VSOP87 无法在可验证的前提下完成，则"星历级精度"这一层**不做**，
并在页面上保留 Standish 并写明其精度边界 —— 用一个未验证的级数冒充星历，比不做更糟。
